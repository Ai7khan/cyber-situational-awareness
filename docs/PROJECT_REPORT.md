# Отчёт о проекте и руководство пользователя
## Интеллектуальная система анализа и мониторинга киберобстановки
**Хакатон DefenceTech · Задача №9 · ВИИРЭиС**

---

## 1. Краткое описание

Разработан рабочий программный прототип с веб‑интерфейсом, который в
автоматизированном режиме принимает разнородные учебные события информационной
безопасности, приводит их к единому виду, классифицирует, устанавливает
взаимосвязи, выявляет аномалии методами искусственного интеллекта, определяет
приоритет и формирует **единую объяснимую картину киберобстановки** с итоговым
аналитическим отчётом.

Ключевые принципы, заложенные в архитектуру:
- **ИИ решает конкретную задачу**, а не является формальным элементом: обнаружение
  аномалий и скрытых последовательностей (ТЗ §6, §7.5).
- **Человек принимает решение**: результаты ИИ — рекомендация, ничего не выполняется
  автоматически (ТЗ §7.5).
- **Полная объяснимость**: любая оценка сопровождается разбором «почему».
- **Прозрачность и настраиваемость**: критерии классификации и приоритизации —
  открытые правила/формулы, редактируемые в интерфейсе.
- **Только синтетические/обезличенные данные**, без подключения к боевым системам (ТЗ §9).

## 4. Архитектура и поток данных

```
        файлы (CSV/JSON/syslog)                 демо‑генератор (ground truth)
                 │                                        │
                 ▼                                        ▼
        ┌───────────────────┐   нормализация + дедуп   ┌───────────┐
        │  ingestion/parsers │ ───────────────────────▶ │  SQLite   │  events + journal
        └───────────────────┘   (каноническая схема)    └───────────┘
                                                              │
                                              ┌───────────────┴───────────────┐
                                              ▼   pipeline (по стадиям)         │
   repetition → anomaly(ML) → correlate(graph) → classify(rules) → priority(formula)
                                              │                                 │
                     обогащённые события ─────┘                                 │
                                              ▼                                 ▼
                              REST API (FastAPI)  ───────▶  React‑дашборд + HTML‑отчёт
```

- **Backend** (Python/FastAPI) — приём, хранение, весь анализ, API, отчёт.
- **Frontend** (React/Vite) — дашборд, граф корреляций, карточки, настройки, журнал.
- **Хранилище** — SQLite (одним файлом), индексы по времени/источнику/категории —
  основа заявленной масштабируемости; при росте нагрузки заменяется на PostgreSQL/DuckDB
  без изменения логики стадий.
- **Модульность**: каждая стадия — чистая функция над списком событий, поэтому
  добавление/замена стадии (в т.ч. LLM) не затрагивает остальные.

## 5. Алгоритмы анализа (ответ на вопрос «какая модель классификации?»)

Важное разделение ответственности — оно и обеспечивает одновременно точность,
скорость и объяснимость:

### 5.1 Классификация категорий — **прозрачные правила** (не «чёрный ящик»)
Категория назначается по приоритету правил:
`аномальное > повторяющееся > взаимосвязанное > требует анализа > информационное`.
Правила настраиваются (пороги повторов, важности) и объясняются одной строкой.
Почему правила, а не ML‑классификатор: для категорий важнее **прозрачность и
воспроизводимость** (критерий «Объяснимость»), а «интеллект» вынесен туда, где он
реально нужен — в обнаружение аномалий и последовательностей.

### 5.2 Интеллектуальный анализ — **машинное обучение + статистика**
- **IsolationForest** (scikit‑learn, обучение без учителя) по поведенческим признакам:
  важность, частота событий от источника в окне, разброс целей (fan‑out), доля отказов,
  редкость типа события, признак нерабочего времени, порт. Даёт нормализованную оценку
  аномальности `0..1` и топ‑факторы (z‑оценки) для объяснения.
- **Правила всплесков** — детерминированно ловят brute‑force и сканирование
  (высокая частота + отказы; большой fan‑out).
- **Марковская редкость переходов** — модель `P(след. тип | пред. тип)` по источнику;
  редкие переходы указывают на **скрытые последовательности** (нетипичный порядок событий).
- На малых наборах (<30 событий) ML отключается (переобучение), работают правила;
  применённый метод указывается в карточке.

### 5.3 Корреляция — **графовые алгоритмы** (networkx)
Рёбра: общий источник в коротком окне (сессии), «кампания» одного источника в длинном
окне (многоэтапные атаки), pivot (`src` одного = `dst` другого — латеральное движение).
Компоненты связности = группы; порядок этапов восстанавливает **kill‑chain**.

### 5.4 Приоритет — **прозрачная взвешенная формула**
```
priority = w1·важность + w2·аномальность + w3·взаимосвязанность + w4·повторяемость + w5·этап_атаки
```
Каждый фактор нормализован в `0..1`; веса и пороги уровней (низкий/средний/высокий/
критический) редактируются в интерфейсе. Хранится вклад каждого слагаемого — отсюда
полная объяснимость итоговой оценки.

### 5.5 Можно ли подключить лёгкую LLM (Qwen3‑0.6B)?
Да, архитектура это предусматривает. Рекомендуемые точки интеграции:
1. **Адаптивная нормализация** неизвестных/свободных форматов логов: LLM извлекает поля
   из произвольной строки в каноническую схему (усиливает `ingestion`).
2. **Естественно‑языковые сводки**: генерация раздела «итоговая оценка» и пояснений к
   группам/аномалиям в отчёте и карточках.
3. **Zero‑/few‑shot триаж и ответы на вопросы** аналитика («почему это критично?»).

Инженерно: `pipeline/classify.py` реализует стадию как функцию над событиями;
LLM‑классификатор добавляется рядом как альтернативная реализация, выбираемая флагом в
`config.py` (напр. `classifier: "rules" | "llm"`), локально через llama.cpp/Ollama/
transformers. Компромиссы: LLM повышает гибкость и качество объяснений, но добавляет
задержку и недетерминизм — поэтому в прототипе основа детерминированная и быстрая, а LLM
рассматривается как усиление, а не замена.

## 6. Веб‑интерфейс

- **Обзор** — баннер оценки обстановки (СТАБИЛЬНАЯ/УМЕРЕННАЯ/ПОВЫШЕННАЯ/КРИТИЧЕСКАЯ),
  KPI, динамика во времени (виден всплеск при атаке), категории, приоритеты, топ‑события.
- **События** — таблица с фильтрами и сортировкой.
- **Корреляции** — группы связей; многоэтапная атака как временная цепочка этапов.
- **Аномалии** — рекомендации ИИ с обоснованием.
- **Журнал** — аудит событий и действий оператора.
- **Настройки** — ползунки весов/порогов → мгновенный пересчёт (демонстрирует
  прозрачность и настраиваемость критериев).
- **Карточка события** — полный разбор «почему»: вклад факторов приоритета, факторы
  аномальности, основания взаимосвязи, правило классификации, исходные поля.
- **Темы** — тёмная (командный пункт) и светлая/печатная; переключатель ☀/☾ (запоминается).

## 7. Сценарий демонстрации (ТЗ §8)

1. **Принять массив данных** — «Демо‑данные» (или «Загрузить» свои CSV/JSON/syslog).
2. **Структурировать** — авто‑нормализация и дедуп в единую базу.
3. **Классифицировать** — 5 категорий на «Обзоре» и во вкладке «События».
4. **Выявить взаимосвязи** — вкладка «Корреляции»: восстановленная kill‑chain и группа brute‑force.
5. **Определить аномалии** — вкладка «Аномалии» с обоснованием (recall 100% на демо).
6. **Определить приоритет** — уровни и разбор в карточке события.
7. **Отобразить обстановку** — дашборд с KPI, динамикой и всплеском.
8. **Сформировать отчёт** — кнопка ▤ «Отчёт» → итоговый аналитический документ.

> Оценивается не только интерфейс, но и способность алгоритма находить закономерности —
> см. метрики (раздел 3) и `python -m data.evaluate`.

## 8. Ограничения и развитие

**Текущие ограничения (осознанные, для учебного прототипа):**
- ML‑анализ рассчитан на реалистичные объёмы (сотни+ событий); на очень малых наборах
  используются правила.
- Хранилище — SQLite (одним файлом); для больших объёмов заменяется на PostgreSQL/DuckDB.
- Приём — пакетная загрузка файлов (не потоковый real‑time).

**Направления развития (ТЗ §12):**
- Локальная LLM (Qwen3‑0.6B и т.п.) — нормализация, сводки, триаж (раздел 5.5).
- Потоковый приём событий, расширение библиотеки сценариев генератора.
- Серверный экспорт в PDF; расширенные модели последовательностей.
- Встраивание как компонента перспективного учебно‑моделирующего полигона.

## 9. Как запустить и проверить

Запуск — см. [README](../README.md#быстрый-старт). Кратко (Windows PowerShell, построчно):
```powershell
cd backend
pip install -r requirements.txt
python -m data.generate
python -m uvicorn app.main:app --port 8000
```
Открыть http://127.0.0.1:8000 → «Демо‑данные».

Проверка точности на эталонной разметке:
```powershell
cd backend
python -m data.evaluate
```
