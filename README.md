# Интеллектуальная система анализа и мониторинга киберобстановки

Рабочий прототип учебной системы ситуационной осведомлённости (mini‑SIEM) для
хакатона **DefenceTech**, задача №9:
*«Разработка интеллектуальной системы анализа и мониторинга киберобстановки»*.

Система в автоматизированном режиме объединяет разнородные учебные события
информационной безопасности, классифицирует их, устанавливает взаимосвязи,
выявляет аномалии с помощью методов ИИ, определяет приоритет и представляет
единую **объяснимую** картину киберобстановки с формированием аналитического отчёта.

Конвейер обработки (ТЗ §6):
```
Источники → сбор/нормализация → классификация → корреляция →
интеллектуальный (ИИ) анализ → приоритизация → визуализация → отчёт
```

> Работает **исключительно на синтетических/обезличенных учебных данных** и не
> подключается к действующим системам (ТЗ §9). Результаты ИИ — **рекомендация**;
> итоговое решение принимает оператор (ТЗ §7.5).

| 7.1 | Сбор данных | Загрузка файлов + демо‑набор; **3 формата**: CSV, JSON, syslog; фиксация времени поступления; история событий |
| 7.2 | Нормализация | Единая каноническая схема; **дедупликация** по хэшу содержимого; группировка |

| 7.5 | Интеллектуальный анализ | **IsolationForest** + правила всплесков + **Марковская** редкость последовательностей |
| 7.6 | Приоритизация | Прозрачная **взвешенная формула**; веса и пороги меняются в интерфейсе |
| 7.7 | Визуализация | Дашборд: KPI, динамика, категории, граф атак, drill‑down до события |

**Тема оформления:** тёмная (командный пункт) и **светлая/печатная** — переключатель ☀/☾.

## Работа с приложением

1. **«Демо‑данные»** — загрузка синтетического набора (3 формата) и авто‑анализ.
2. **Обзор** — оценка обстановки, KPI, динамика во времени, категории, приоритеты,
   наиболее значимые события.
3. **События** — таблица с фильтрами (категория, приоритет, только аномалии) и сортировкой.
4. **Корреляции** — взаимосвязанные группы; многоэтапная атака отображается как
   временная цепочка (kill‑chain).
5. **Аномалии** — рекомендации интеллектуального анализа с обоснованием.
6. **Журнал** — аудит всех событий и действий оператора.
7. **Настройки** — изменение весов/порогов → **мгновенный** пересчёт анализа.
8. **Отчёт** — аналитический документ с итоговой оценкой (кнопка ▤, печать в PDF из браузера).

Клик по любому событию (в таблицах или на графе) открывает карточку с полным
разбором «почему»: вклад каждого фактора в приоритет, факторы аномальности,
основания взаимосвязи и правило классификации.

> Демо‑набор проходит **тот же** конвейер, что и любой загруженный/боевой набор —
> анализ и отчёт полноценно работают и на демо‑данных, и на данных организаторов.

## Загрузка своего набора данных

Кнопка **«Загрузить»** принимает один или несколько файлов **.csv / .json / .log**.
Формат определяется автоматически; каждый источник приводится к единой
**канонической схеме**. Неизвестные поля не теряются — они сохраняются в `tags`.

### Каноническая схема и сопоставление полей
Парсер сам сопоставляет распространённые имена столбцов/ключей (регистр не важен;
для JSON поддерживается вложенность через точку, напр. `source.ip`):

| Каноническое поле | Принимаемые имена в источнике |
|---|---|
| `event_time` | `event_time`, `timestamp`, `@timestamp`, `time`, `ts`, `datetime`, `date` |
| `event_id` | `event_id`, `id`, `event.id`, `uid`, `uuid` |
| `src_ip` | `src_ip`, `src`, `source.ip`, `source_ip`, `srcip`, `source` |
| `dst_ip` | `dst_ip`, `dst`, `destination.ip`, `dest_ip`, `dstip`, `destination` |
| `user` | `user`, `account`, `username`, `user.name`, `usr` |
| `action` | `action`, `event.action`, `act` |
| `raw_type` | `raw_type`, `type`, `event.type`, `event_type`, `signature`, `alert` |
| `protocol` | `protocol`, `proto`, `network.protocol` |
| `port` | `port`, `dst_port`, `destination.port`, `dport` |
| `status` | `status`, `result`, `outcome`, `event.outcome` |
| `raw_severity` | `raw_severity`, `severity`, `severity_num`, `sev`, `score`, `level` |
| `host` | `host`, `hostname`, `host.name`, `device`, `computer` |
| `kill_chain_stage` | `kill_chain_stage`, `stage`, `kill_chain_phase`, `phase` |
| `message` | `message`, `detail`, `msg`, `description`, `text` |

**Важность (`raw_severity`)** принимает число `0..100` **или** текстовую метку:
`info=10, low=25, medium/warning=50, high/error=75, alert=90, critical=95, emergency=100`.

**Этапы kill‑chain** (`kill_chain_stage`): `recon, delivery, exploitation, installation,
command_control, lateral_movement, exfiltration` — используются для корреляции и приоритета.

### Минимальные требования к данным
- Обязательно полезно: **временная метка** и **источник** (`src_ip`/`host`).
- Желательно: `raw_type`/`signature`, `raw_severity`, `status`, `dst_ip`, `user`.
- Нет метки времени → используется время поступления; нет `event_id` → генерируется.

### Примеры

**CSV** (свои имена столбцов — всё сопоставится автоматически):
```csv
time,source_ip,dest_ip,username,event_type,level,proto,port,outcome,description
2026-09-19T08:05:00Z,45.83.140.77,10.0.10.11,root,port_scan,high,tcp,0,alert,external SYN sweep
2026-09-19T08:05:20Z,45.83.140.77,10.0.10.11,root,web_attack,critical,tcp,443,alert,SQLi on /login
```

**JSON** (массив объектов или `{ "events": [ ... ] }`, вложенность ECS поддерживается):
```json
[
  { "@timestamp": "2026-09-19T08:05:00Z",
    "source": { "ip": "45.83.140.77" },
    "destination": { "ip": "10.0.10.11", "port": 443 },
    "event": { "type": "web_attack", "action": "exploitation" },
    "severity_num": 60, "message": "SQLi on /login" }
]
```

**syslog** (RFC5424 со структурированными данными `key="value"`):
```
<131>1 2026-09-19T08:05:00Z srv-web01 host-agent - - [evt type="malware_detected" src="45.83.140.77" sev="72" stage="installation"] webshell dropped
```

### Если имена полей не распознаются
Добавьте синоним в одну строку таблицы `FIELD_ALIASES` в
[`backend/app/ingestion/parsers.py`](backend/app/ingestion/parsers.py) — например,
`"src_ip": [..., "ip_src", "attacker_ip"]`. Перезапуск не требует изменений схемы БД.

## Как работает анализ

Конвейер выполняется по стадиям (в порядке зависимостей), каждая — отдельная функция
над списком событий (см. [`backend/app/pipeline/`](backend/app/pipeline)):

1. **Повторяемость** — частота одинаковых сигнатур в скользящем окне.
2. **Интеллектуальный анализ (ИИ):**
   - **IsolationForest** (обучение без учителя) по поведенческим признакам
     (частота от источника, разброс целей, доля отказов, редкость типа, нерабочее время);
   - **правила всплесков** (brute‑force / сканирование);
   - **Марковская редкость переходов** — необычный *порядок* событий (скрытые последовательности).
   Для очень малых наборов (<30 событий) ML‑модель отключается, работают правила
   (в карточке события указывается применённый метод).
3. **Корреляция** — граф (networkx): рёбра по общему источнику во времени, по «кампании»
   одного источника и по pivot (src↔dst); компоненты связности = группы, восстановление kill‑chain.
4. **Классификация** — прозрачные правила → категории: информационные / требуют анализа /
   аномальные / повторяющиеся / взаимосвязанные.
5. **Приоритизация** — взвешенная сумма нормализованных факторов
   `важность · аномальность · взаимосвязанность · повторяемость · этап атаки`
   → низкий / средний / высокий / критический (веса меняются в UI).

**Почему не «чёрный ящик»:** категории и приоритет — прозрачные правила/формула, а ИИ
применён там, где он действительно нужен (аномалии и скрытые последовательности), что
обеспечивает высокую **объяснимость** и скорость. Точка расширения для LLM
(напр. Qwen3‑0.6B) описана в [дальнейшем развитии](#дальнейшее-развитие).

## Метрики и оценка
На демо‑наборе (`cd backend && python -m data.evaluate`):
- Точность классификации: **~96%**
- Обнаружение аномалий: **recall 100%**, F1 ~**88%**
- Корреляция: **100%** восстановление заложенных групп (brute‑force и kill‑chain)
- Обработка ~1050 событий за **~0.6–0.8 сек** (~1500 событий/сек)

Соответствие критериям оценки (ТЗ §11) и пунктам ТЗ §1–§13 —
см. [docs/PROJECT_REPORT.md](docs/PROJECT_REPORT.md).

## Дальнейшее развитие
- **LLM (напр. Qwen3‑0.6B) локально** — три точки интеграции: (1) адаптивная
  нормализация неизвестных/свободных форматов логов, (2) естественно‑языковые
  сводки и объяснения в отчёте, (3) zero‑shot триаж и ответы на вопросы аналитика.
  Конвейер модульный: LLM‑классификатор подключается рядом с правилами в
  `pipeline/classify.py` без изменения остального.
- Потоковый приём событий в реальном времени, расширение сценариев генератора,
  экспорт отчёта в PDF на сервере, интеграция с внешними источниками (в боевом контуре).

> Прототип может стать функциональным компонентом перспективного
> учебно‑моделирующего информационного полигона (ТЗ §12).
